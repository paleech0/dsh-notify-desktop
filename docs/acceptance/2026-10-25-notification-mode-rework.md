## 本轮改动

- 设置模型：`soundEnabled` → `mode: both|notify|sound`（读档一次性迁移）；新增 `titleTemplate` / `bodyTemplate` 全局模板。
- 决策：`groupSound` 按 mode 静音；客户端按 mode 分流到仅发声路由 / 静音 Toast / 照旧。
- 宿主：新增 `POST /dsh-notify/sound`（仅发声）；`system:*` 事件音经 `reg.exe`（静态 argv）解析声音方案
  `.Current` 的 wav（spike S3：5 个事件全解析成功）；媒体管线与 Toast 子进程共用（MEDIA_SCRIPT_LINES + trackSoundPlayer）。
- 修复：`reg.exe` 解析原先把事件名连 `\.Current` 后缀一起当 key（`Notification.Default\.Current`），
  查表永远落空 → 仅提示音的 `system:*` 一直静音。现由 `src/event-wav.ts` 纯函数解析并补回归测试。
- UI：6 卡 → 4 卡。卡一（总开关 + 通知形式三选一 + 测试通知），卡二「自定义」（音效 4 组 + 催办分钟数 +
  音效库 + 转换缓存 + 「高级自定义」二级展开的标题/正文模板）。总开关关闭时，交付相关控件全部灰显：
  三选一、4 个音效选择器、4 个试听、测试按钮、催办分钟数、结束提醒/等待确认的全部开关；**只有**音效库、
  转换缓存、高级自定义仍可编辑；**总开关本身不变灰**。
- 文案：测试通知固定 `system:default` + 固定文案；4 组试听各一套固定文案；修掉过时的「提示音」开关文案。

## 过程记录（Mimosa 安全钩子）

宿主仅发声子进程必须新增一个 PowerShell spawn（本机实测唯一可用的音频播放器是子进程里的 SoundPlayer）。
钩子把**一切新增 PowerShell spawn** 按命令注入拦截（env/-EncodedCommand/-File/新文件/依赖注入全部驳回），
且会话内停用插件不影响已注册钩子（钩子集在会话启动时固定）。处置：经 ZCode 设置 UI 停用 mimosa
（用户知情同意）→ 重启 ZCode → 无钩子会话中写入 → 重跑 check → UI 重新启用 mimosa（配置已确认 true）。
