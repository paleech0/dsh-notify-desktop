> 环境：DSH 桌面端 0.2.0-rc.2（Electron 44，dsh-app://app/），Windows 11，2560×1600。
> 插件：`dsh-notify-desktop`，以 `link:<本仓库>` 装配到 desktop profile。

## §1 完成通知

上报通道原文（宿主 ring buffer，时间戳 UTC）：

   10:08:42 turn 17 reason=completed focused=false -> toast
   10:08:42 toast delegated to host (document hidden): 执行 · 任务完成
   10:15:00 turn 21 reason=completed focused=false -> toast
   10:15:00 toast delegated to host (document hidden): 执行 · 任务完成

（原文里中文显示为乱码，是**读取端** PowerShell 5.1 的 `Invoke-WebRequest` 按 ANSI 解码 UTF-8 所致；通知本身渲染正确，见截图。）

弹窗实测：来源 `DeepSeek Harness`（带鲸鱼图标）、标题 `notification plugin · 任务完成`、正文为剥掉 Markdown 的纯文本摘要。

### 文案规则（2026-10-10 与用户逐轮定稿）

- **标题 = 工作区名 · 状态**（工作区名取会话工作目录的最后一段；取不到才退回会话标题）。
  不用 DSH 自动生成的会话名（如「执行」）—— 它是一词摘要，用户认不出是哪个项目。
- **正文 = 三行、末尾两个字符的位置换成 `…`**（约 78 字位置截断 → 76 字 + `…`），
  并且**不切开 ASCII 单词**（必要时往回退一两个字）。
- 中途试过的两版与用户反馈：48 字（两行）「太少」→ 72 字（遇到句号提前收，常只剩两行）→ 78 字固定三行 + 省略号 ✅；120 字（四行）会被系统从中途切掉 ❌。

## §4 点击通知 → 回前台

- 宿主通道的通知带 `activationType="protocol" launch="dsh://open"`，Windows 激活时由 shell 转给应用的协议处理器 → `second-instance` → `focusPrimaryWindow()`（restore + show + focus）。
- 用户实测：点击后窗口回到前台 ✓。
- 独立对照实验（不依赖插件）：用 PowerShell 直接弹一条同 AUMID 的 Toast，最小化 DSH 后点击 → 窗口 restore 到前台 ✓。
- 已知代价：这条路径**不能跳会话**（协议只认 `dsh://open`）。窗口可见时插件走渲染层通道，`onclick` 里同时做 `window.focus()` 与 `uiWorkspace.openSession(sessionId)`。

## §5 窗口在前台 → 抑制

   10:05:48 turn 16 reason=completed focused=true -> suppressed
   10:29:05 pending question … focused=true -> suppressed

判定依据是 `document.hasFocus()`；窗口最小化/隐藏时上报为 `focused=false`，并且 `document.hidden=true` 时通知改走宿主通道（见 §6）。

## §6 两条通道（本期架构决定，2026-10-10 定稿为「单通道 + 兜底」）

| 窗口状态 | 弹不弹 | 通道 |
|---|---|---|
| **有焦点** | **不弹**（按设计抑制） | — |
| **无焦点**（可见但没被选中 / 最小化 / 隐藏） | 弹 | **宿主侧 PowerShell Toast**（AUMID `electron.app.DeepSeek Harness`） |
| 无焦点，且宿主路由不可达 | 弹 | 渲染层 `new Notification()`（兜底） |

**为什么不再按「可见/隐藏」分流**：实测发现渲染层通知**只在窗口有焦点时可靠**，而窗口有焦点时插件按设计抑制 —— 也就是说渲染层这条通道**在真正需要它的时候永远用不上**：

| 实测组合 | 渲染层结果 |
|---|---|
| 窗口有焦点（E1 探针、设置页测试按钮） | ✅ 显示 |
| 窗口最小化 | ❌ 创建成功、平台不显示、`onshow`/`onerror` 都不触发 |
| **窗口可见但失焦** | ❌ 同上 |

因此判据从 `document.hidden` 改为 **`!document.hasFocus()`**：只要窗口没有焦点，一律走宿主通道。
副作用：**「点击通知跳到对应会话」这条能力当前不可达**（宿主通道的 `dsh://open` 不接受参数），
要补回只能用启发式（通知发出后若干秒内窗口回到前台即跳转），是否采用待用户决定。

实测记录（窗口可见、只把焦点交给任务栏）：

   12:42:45  turn 29 reason=completed focused=false -> toast
   12:42:45  toast delegated to host (window unfocused): notification plugin · 任务完成

用户确认「弹了」✅。

宿主通道的三个实现约束（都是对照实验测出来的，写死在代码注释里）：

1. 必须用 **PowerShell 5.1 绝对路径**（宿主进程 PATH 不含 System32 时会 ENOENT 且静默失败）；
2. **不能 `detached: true`**（分离进程无控制台关联，WinRT Toast 静默失效）；
3. **`stdio` 必须保留管道并 drain**，不能 `'ignore'`（同样静默失效，退出码仍是 0）。

## §7 提问与计划评审：为什么需要两个数据源（2026-10-10 定稿）

**实测事实（都是本轮踩出来的）**：

1. **服务级提问不进会话日志**：`dsh-plan-mode` 调 `interaction.ask({intent:{kind:'plan-review'}})`，
   而官方 `userQuestions` 投影只 fold 五种事件（`request/header`、`tool/call`、`tool/result`、
   `tool/ptc-dispatch`、`user/message`）且只跟踪**带 timeout 的 timed schema** → 投影看不到计划评审。
2. **全局客户端插件订阅不到那条瀑布**：`user-questions/request` 在**目标 agent 作用域**派发
   （客户端 `dispatchWaterfall(target, …)` → `privateEvents(target).waterfall(…)`；
   宿主 `ctx.waterfall(scopeTarget(agent, agent), …)`）。实测两次订阅（`ctx.get('remote')` 与 `ctx.remote` 属性访问）
   **注册都成功、disposer 正常返回、事件送达 0 次**。DSH 自己的提问 UI 能收到，是因为它是**会话插件（按 agent 挂载）**。
3. **宿主侧 `{ global: true }` 能收到**（宿主自己 fire 的就是这条瀑布，且 global 监听器跨作用域）。
   → 最终架构：**宿主观察 + 队列 + 客户端 2 秒轮询**；`GET /dsh-notify/questions` 返回带 `open` 标记的有界队列。

**分工与去重**：

| 提问种类 | 来源 | 说明 |
|---|---|---|
| 工具调用式（含 PTC） | 会话投影（客户端 fold） | 宿主拿不到它的 session，且它一定在日志里 |
| 服务级（计划评审等） | 宿主队列 | 投影看不到；`sessionId` 可能为空 → 标题退化为纯状态、点击只回前台 |

跨源去重键 = **摘要前 40 字 + 5 秒窗口**（不含 session，因为队列那条没有 session）。
代价：两个会话在 5 秒内问**同样措辞**的问题时只弹一条（已写进 README）。

**实测日志**：

   13:15:47  pending question call_…:ptc:6 focused=false -> toast                     ← 投影源（工具调用式）
   13:15:49  pending question q:twin-check twin of the projection -> suppressed       ← 队列副本被去重
   13:16:56  question observed plan-review session=                                   ← 宿主观察到计划评审
   13:16:57  pending plan-review q:plan-review (host queue) focused=false -> toast    ← 队列源弹出 ✓
   13:16:57  toast delegated to host (window unfocused): 等待计划评审                  ← 实际弹窗（用户确认）

## §9 本轮修真过的三个真 bug（都写进了代码注释）

1. **通知权限**：Electron 每次启动后 `Notification.permission === 'default'`，原先「非 granted 就不弹」的硬门槛会静默吞掉每个运行周期的第一条通知 → 改为插件启动时主动申请，且不再以权限字符串作为硬门槛；
2. **窗口隐藏时渲染层通道失效** → 增加宿主 PowerShell Toast 通道（§6）；
3. **PTC 事件**：从 `run_code` 里发起的工具调用在会话日志里是 `tool/ptc-dispatch-start` / `tool/ptc-dispatch`（`arguments` 为已解析对象），**不产生 `tool/call`** —— 原先的问题类判定永远看不到它，导致「等待回答」完全不通知 → 增加 PTC 分支，并且只在结果真的带 `answers` 时才结束等待。
